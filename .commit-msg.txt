fix: ignore role assignment principalType drift by default

The identity-type fix resolved the previous idempotency failure, but
a second e2e run for examples/large-parameter-set surfaced a related
issue: the second plan proposed an in-place update to
module.test.azapi_resource.role_assignments["current_user_reader"],
changing properties.principalType from "ServicePrincipal" back to
null.

Azure's Microsoft.Authorization/roleAssignments GET API does not
reliably return principalType on refresh, even when it was supplied
at creation. The field also cannot be changed after creation (it
forces replacement), so there is no configuration drift to actually
surface here -- only a refresh artifact.

Defaults ignore_body_changes.authorization_role_assignments to
["properties.principalType"] so this refresh artifact does not cause
every subsequent plan to show a spurious update. Callers can still
override the default if needed.

Verified locally: avm pre-commit and avm lint both pass, and all 5
unit tests still pass.
